# AI Model Connector, Plan F: Shadow, Promotion, Campaign Dry Run and Counters Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A gated candidate (Plan E) can be put in shadow, is scored beside the active model on live mail without ever touching a case, is compared (class, would-be verdict, campaign dry run, alert delta), and an admin can promote it, roll back, discard it or extend the shadow period, with every condition of the spec enforced on the server.

**Architecture:** The inference server scores `active` and `shadow` in one classify call and isolates a shadow failure. Django owns the truth: the registry says which version is active and which is shadow, and one idempotent `sync_server` pushes that state to the server after every pointer move and every five minutes (so a server restart heals). The shadow answer is stored per case (`ShadowResult`) when the AI job closes. The would-be verdict is recomputed in `get_report` from the same pure inputs as the live verdict. The campaign dry run reads the live collection and records its effect in the database only. Promotion conditions live in one service module that the REST API calls.

**Tech Stack:** FastAPI (inference server), Django and DRF, Celery, ChromaDB client (read only), the pure scoring engine.

**Spec:** `docs/specs/2026-10-30-ai-model-connector-design.md` sections 3 (registry, stats), 6 (shadow, dry run, promotion), 7 (campaigns), 8 (API), 10 (health). Master plan: `docs/plans/2026-10-30-ai-model-connector.md`, Plan F. Plans A to E are merged in the local `design/ai-model-connector` branch (Plan E at `384b3aa7`).

## Guidance used

Pages named from prior reading and not re-fetched while writing this plan; check them before relying on a detail. Where a page does not answer the question it is said.

- MLflow, [model registry workflow](https://mlflow.org/docs/latest/ml/model-registry/workflow/): serving code follows an alias that is a mutable pointer to a version. The page does not document rollback. Here `active` and `shadow` are those pointers, and rollback is the pointer moving back, as Plan E's registry already does.
- Google, [MLOps continuous delivery and automation pipelines](https://cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning): a candidate is validated offline and online before it serves, and a registry keeps the previous version for rollback. Nothing in it prescribes shadow thresholds, so the 7 days and 500 mails are the spec's own calls (C7).
- ChromaDB, [query and get](https://docs.trychroma.com/docs/querying-collections/query-and-get): `query` takes `where` metadata filters and `n_results`; `get` pages with `limit` and `offset`. Neither changes data, which is what the dry run relies on. The project's Chroma proxy blocks collection deletion and PUT (Plan B notes), so no task creates and drops collections.
- FastAPI, [running blocking work in a thread pool](https://fastapi.tiangolo.com/async/): sync work in `run_in_threadpool` does not block the event loop. A thread cannot be killed on a timeout: `asyncio.wait_for` stops waiting, not running. Task 1 states that cost.
- Celery, [Redis broker notes](https://docs.celeryq.dev/en/main/getting-started/backends-and-brokers/redis.html): tasks stay under the visibility timeout, so seeding runs in short self-requeueing chunks.

## Review Focus

- A shadow classify that raises, times out or returns garbage leaves the case, its fields and its finalisation exactly as without a shadow (Tasks 1, 3).
- The would-be verdict is computed from the inputs of the live pass: no second `collect_signals`, no extra `times_sent` increment, no second write of IOC levels (Task 4).
- A promote request with an unreviewed Safe/Dangerous flip, an unreviewed campaign in the alert delta, fewer than 500 live shadow results, a shadow younger than 7 days, a stale or failed gate recheck or a running training job is refused by the service, whatever the client sent (Task 9).
- Two simultaneous promote clicks, or promote during a rollback, end with exactly one active version and consistent events (Task 9).
- A reload the server refuses (4xx) after a promote reverts the pointer; a reload that fails transiently keeps the registry as truth and `sync_server` heals it; a server restarted with empty state is brought back to the registry state within five minutes (Task 2).
- The dry run writes nothing to the live collection, creates no `Campaign` or `CampaignMember` and emits no event (Task 6).
- Reviews are append-only and a review of a flip that no longer exists is refused (Task 9, 10).
- A non-admin gets 403 on writes, a user outside Admin and CISO gets 403 on reads, nobody is anonymous (Task 10).

## Calls made in this plan

- **Ruling F1: one classify call, shadow isolated on the server.** `versions` may be `["active"]`, `["active", "shadow"]` or `["shadow"]` (the last for seeding and the replay); anything else is 400. With a shadow requested, the server answers the active part first, then runs the shadow inside `asyncio.wait_for(..., SHADOW_TIMEOUT)` (default 8 s, env `AI_SHADOW_TIMEOUT`, shorter than the connector's 20 s) and returns `results.shadow` as the answer or `{"error": "<ClassName>"}` (`NoShadow`, `Timeout`, or the exception class). A shadow error is never an HTTP error when `active` was asked. `["shadow"]` with no shadow loaded is 409. Cost if wrong: on timeout the worker thread keeps running to its end and holds a slot meanwhile; the slot limit bounds the damage.
- **Ruling F2: the registry is the truth and the server follows it.** `ai_model/serversync.py` builds the wanted state (active and shadow versions with presigned URLs and manifest hashes) and compares it with `GET /v2/models/ai_mail` (version ids only). It pushes `POST /v2/reload` after every pointer move and from a beat entry `ai-model-server-sync` every 300 s, and it is what makes a restarted server serve the right model again (the server keeps loaded models in memory only). A reload the server refuses with 4xx after a pointer move reverts the pointer and raises; a transient failure leaves the pointer and the beat retries. The health detail says "registry and server differ" until synced. Cost if wrong: up to five minutes of the old model after a transient failure; the answers carry their version, so nothing is mislabelled.
- **Ruling F3: one shadow at a time, started explicitly.** `ModelVersion.shadow_slot` (nullable unique, as `active_slot`) plus a NULL-safe CHECK. `set_shadow` accepts only a `candidate` whose manifest gate is eligible and refuses while another shadow exists, so an admin discards first. It records `shadow_since`, queues the seeding (F8) and pushes the server state. No automatic shadow start (D6: nothing becomes live without an admin). Cost if wrong: one more click.
- **Ruling F4: the shadow answer is stored when the AI job closes.** `finish_provider_analysis` stores a `ShadowResult` after its own transaction, in a try/except that logs the class. The answer is dropped when its version is not the registry's current shadow (a promote or discard raced it). One row per (case, version); a redo of the analysis overwrites it. Cost if wrong: a lost shadow row for that case, which only lowers the count. *Amended in the fix wave: the row is stored inside the closing transaction, in a savepoint, before the reconcile is queued, so the would-be verdict always finds it.*
- **Ruling F5: the would-be verdict reuses the live pass.** `get_report` already holds `signals`, `deny_listed`, `deny_reason` and the votes. After the live verdict it calls `score_case(signals, shadow_ai, deny_listed, shadow_missing, deny_reason, votes=collect_votes(case, shadow_ai))` and applies the same embedded evidence (Task 4 splits the impure evidence step from the pure escalation so both verdicts share one evidence read). With the `scoring.mail_embedded_categorical` kill switch off, the would-be fields stay empty. Any exception is swallowed with a log line. `shadow_ai` maps like `ProviderResult` (score rounded, confidence percent capped at 100, `INCONCLUSIVE` means missing). Cost if wrong: a refactor of `reports.py` that the existing scoring tests must prove behaviour-neutral.
- **Ruling F6: flips.** Per result: `same`, `changed` (any difference of the case result) and `critical` (Safe to Dangerous or Dangerous to Safe, the two the spec requires reviewing; Inconclusive and Suspicious are never critical). The review list shows all changes, the promote condition counts only critical ones (C7).
- **Ruling F7: the dry run uses the live collection for geometry and the database for the candidate's classes.** The campaign embedding is the same `cmp-e1` vector whatever the classifier, so neighbours come from the live collection; what differs is which neighbours the candidate calls Dangerous. The dry run queries 60 nearest neighbours without the class filter, keeps those whose case the candidate called Dangerous (a `ShadowResult` of the same version, live or seeded), and applies the live threshold and member rules. This replaces the spec's separate shadow collection (section 6) because the proxy blocks deleting collections, a second collection would outlive every shadow, and the cleanup connector watches only the live name. Cost if wrong: neighbours beyond rank 60 are missed on the shadow side (the live query uses 20 Dangerous ones); the table shows the counts, and the spec text is amended (Task 11).
- **Ruling F8: seeding.** At `set_shadow`, a Celery task classifies the live collection's documents with the shadow (`versions: ["shadow"]`, the stored document text, chunks of 25, self-requeueing, stops at 20 minutes of work per run) and stores `ShadowResult` rows with `origin="seed"`, no would-be verdict. Documents without a case id or a case are skipped. Seed rows count toward the dry run, not toward the 500 mails (the condition counts `origin="live"`). Cost if wrong: about 1,300 classify calls at shadow start.
- **Ruling F9: the alert delta.** For the shadow's period, per case with a dry-run effect: `candidate_only` (effect would create or would join, and the live case is in no campaign), `active_only` (the live case is in a campaign and the effect is none or no check). Review items are keyed by case id and kind. Cost if wrong: a coarse unit (cases, not campaigns); the table groups by live campaign reference where one exists.
- **Ruling F10: counters.** `ModelVersionStats` is recomputed for the last three days by a daily beat task from `AiAssessment` (per `model_version`: scored, Dangerous), `CampaignMember` and the `ConnectorDelivery` rows of the TheHive connector for `campaign_updated`, attributed through the case's assessment version. Purity: over 30 days, among campaign members that have an active label, the share labelled Dangerous; the warning needs at least 10 labelled members and a purity below 80% (C34). Model age warning at 60 days (C11). Cost if wrong: counters lag by up to a day.
- **Ruling F11: the gate recheck is a server job without output.** `TrainParams` gains `recheck: bool = False`. A recheck job runs the gate on the current ledger with the shadow's recipe and seed, skips the final fit and the bundle upload, and returns the report. Django stores `{job_id, passed, finished_at}` on `ModelVersion.recheck`; only a recheck that finished after the shadow period minimum was met and less than 7 days ago counts. Cost if wrong: one more job type in the worker; no bundle is written, so nothing can be promoted from it.
- **Ruling F12: promotion conditions, all enforced in `promotion.can_promote(version)`**: status `shadow`; at least `shadow_min_days` (7, extendable) since `shadow_since`; at least 500 live shadow results; every critical flip reviewed; every candidate-only and active-only item reviewed; a counting recheck that passed; when the candidate's campaign profile differs from the active one, at least `window_days` (15) of dry run (C29); no running `RetrainJob`. It returns the list of unmet conditions, and `promote` raises with that list. Cost if wrong: a stricter or looser threshold is a constant.
- **Ruling F13: promote, rollback, discard, extend.** Promote and rollback are `set_active` then `sync_server` (F2). Rollback is allowed only when a `previous` exists. Discard works on candidate and shadow versions and clears the shadow slot. Extend sets `shadow_min_days` upward only. Each takes `select_for_update` on the version rows and writes a `ModelEvent` with user and note. Concurrent clicks are serialised by the locks; the second sees the new state and is refused. Stored results of earlier cases are never recomputed (spec section 6).
- **Ruling F14: roles.** New `IsAdmin` (group `Admin`) for writes and `IsAdminOrCISO` for reads, in `api/permissions/ai_model.py`, following spec C8 (the connector endpoints use `IsAdminOrCERT`, which the spec does not name for this card). Cost if wrong: one class changes.
- **Ruling F15: the engine replay is a sensitivity study, not an oracle.** `ai_model_engine_replay` rebuilds non-AI signals read-only from the ledger as `score_process/management/commands/backtest_scoring.py` does, replays recent finalised mail cases with the live AI signal and with the shadow's, and prints the transition matrix, the critical flips and the Inconclusive change. Its result is a precondition for the operator's first promotion (a decision about the engine's reaction to calibrated confidence), not for building Tasks 6 to 11. It needs the candidate to be the loaded shadow.
- **Ruling F16: the version 0 temperature fit (Ruling E20) is not built.** Version 0 keeps showing "confidence not calibrated" until the first promotion replaces it; a v0 calibration file would need a v0 bundle that exists only to be replaced. Cost if wrong: no tiers for v0 mails in the meantime. Revisit if the first promotion is delayed past the shadow period.

## Contracts

- Server classify: `POST /v2/models/ai_mail/classify` body `{"mail_body", "versions": ["active"] | ["active","shadow"] | ["shadow"], "exclude_case_ids"}`; answer `results: {"active": {...}?, "shadow": {...} | {"error": str}?}` (the active shape is unchanged), `campaign_embedding`, `campaign_embedding_version`, `latency_ms`. `["shadow"]` returns 409 when none is loaded.
- `AiInferenceClient.classify(mail_body, exclude_case_ids=None, versions=("active",)) -> dict`.
- `ai_model.registry`: `set_shadow(version, user, note="") -> ModelVersion`, `clear_shadow(...)` inside `discard`, `reload_payload(active, shadow) -> dict`; `ModelVersion` gains `shadow_slot`, `shadow_since`, `shadow_min_days` (default 7), `recheck` (JSON).
- `ai_model/serversync.py`: `wanted_state() -> dict`, `server_matches(client) -> bool`, `sync(client=None) -> bool`; task `ai_model.tasks.sync_server`.
- `ai_model.models`: `ShadowResult(case, version FK, origin live|seed, result, sub_class, score, confidence, probabilities, tier, error, live_result, would_be_result, would_be_score, would_be_confidence, would_be_rule, flip none|changed|critical, created_at)` unique (case, version); `ShadowCampaignEffect(case, version FK, effect no_check|none|would_create|would_join, member_case_ids JSON, live_campaign FK null, created_at)` unique (case, version); `ShadowReview(version FK, kind flip|campaign, case_id, user, note, at)` append-only; `ModelVersionStats(version FK, day, scored, dangerous, campaign_checks, created, joined, alerts)` unique (version, day).
- `ai_model/promotion.py`: `can_promote(version) -> list[str]` (unmet conditions), `promote(version, user, note)`, `rollback(user, note)`, `extend(version, days, user, note)`, `review(version, kind, case_id, user, note) -> ShadowReview`.
- `score_process/scoring/cortex_analyzers/reports.py`: `_embedded_evidence(case, mail) -> Evidence | None` (the impure half, writes levels once) and `_escalate(verdict, evidence)` (pure); `_apply_embedded_escalation` becomes their composition.
- REST (all under `/api/ai-model/`): `GET status/`, `GET versions/`, `GET shadow/` (comparison, flips, campaign effects, alert delta, conditions), `POST shadow/start/`, `POST promote/`, `POST rollback/`, `POST discard/`, `POST extend/`, `POST reviews/`, `GET reviews/`, `POST recheck/`.
