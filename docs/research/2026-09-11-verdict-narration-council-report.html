LLM Council: Verdict Narration Model

Pressure-testing a proposed generative report-writer for Suspicious (Thales CERT) · 2026-09-11
The question brought to council Should Suspicious build a generative "verdict narration" model — teacher distillation from a hosted LLM into a fine-tuned Qwen2.5-7B-Instruct via LoRA/QLoRA, deployed on-prem — to turn analyzer reports plus a case's already-computed verdict/score/confidence into a rich, plain-language report for non-technical stakeholders? The verdict itself must never be re-derived or contradicted by the model. Team: a solo technical lead plus an AI coding agent, no dedicated ML infra, one prior CPU-trained classifier as ML experience.

Council Verdict

Where the Council Agrees

  • "Fixed verdict, never re-derived" is not a training-time property. No advisor believes LoRA, distillation, or model choice affects this. Four of five land on the same mechanism: template-lock the verdict/score/band as literal injected strings, then run a deterministic post-generation validator that rejects/regenerates on mismatch. This is code, not model behavior — needed under every architecture on the table.
  • The distillation pipeline is solving an unproven problem. Four of five advisors say: try prompting the base model first. Nobody described running that experiment before committing to teacher distillation, LoRA, and rented GPUs.
  • Solo-lead bandwidth is a real constraint, not a footnote. One person cannot also be the data pipeline, training infra operator, quality evaluator, and deployer for a document reaching external stakeholders.
  • The open-source framing (open model/code, closed dataset) is fine. The Alpaca precedent settled this — flag and revisit later, not a blocker.

Where the Council Clashes

The Expansionist vs. everyone else — and it's lopsided. The Expansionist calls the fixed-verdict architecture a reusable "moat" and proposes generalizing the schema now plus spinning off adjacent fine-tunes from the same ToS-encumbered teacher data. Every peer reviewer, independently, 5 for 5, named this response the weakest: it never engages enforceability or the solo-lead constraint, and its own proposal increases the maintenance surface for someone already stretched thin. Its one salvageable idea — a generic input schema (verdict + evidence + confidence) rather than phishing-specific fields — is worth keeping; the rest of the expansion agenda should be shelved.

Train now vs. prompt first is softer — a matter of sequencing, not real disagreement. Nobody argues for jumping straight to LoRA. The spectrum runs from "prompting probably suffices" to "prompt first, keep a numeric go/no-go gate for later fine-tuning."

Blind Spots the Council Caught

  • Data governance, not just redistribution ToS. Four of five peer reviewers independently flagged: sending raw case data — phishing emails, VT/GTI/MISP intel, mail analyzer output — to a hosted third-party API to generate teacher training text is a confidentiality/compliance question for a CERT, separate from and arguably more serious than the redistribution-ToS question every advisor discussed. "Historical/synthetic case shapes" was asserted as low-risk without examination.
  • Staleness lifecycle of the fine-tune itself. A distilled model bakes in phrasing tied to the deterministic engine's rules at training time. When those rules change (as they just did, in the whole-branch review), the model's learned narrative patterns go stale in weights, not in a cache — a slower-motion, harder-to-detect version of the exact bug that motivated this whole safety constraint.
  • Also worth carrying forward: no human sign-off gate before an AI-narrated report reaches an external stakeholder; no plan for validating factual faithfulness of entities/numbers beyond the verdict string itself.

The Recommendation

Do not start the teacher-distillation pipeline yet. The proposal as written skips the cheap experiment that would tell you whether you need it, and builds the expensive one first.
  • Build the deterministic verdict-lock + output validator now, regardless of generation approach — this is the actual fix for the bug class you're worried about, and it's a day of work, not a training run.
  • Prompt an on-prem instruct model against real case data with the locked verdict injected, and get an analyst to read the output. This answers "is fine-tuning even necessary" empirically instead of by hunch.
  • Treat fine-tuning as contingent: gated on the prompted baseline demonstrably failing, and on having 200+ genuinely distinct cases with teacher outputs in hand before renting any GPU.
  • Resolve the data-classification question before any teacher API call touches real case content — that's a harder blocker than anything in the original design.
  • Shelve the Expansionist's platform-wide ambitions. A slightly generic input schema now is cheap; spinning off a family of fine-tunes from ToS-encumbered data before the first version ships is not something a solo lead should be doing.

The One Thing to Do First

This afternoon, before touching LoRA or a rented GPU: build the deterministic verdict/score/band injector-and-validator (inject as literal strings, regex/schema-check the generated output, fail closed to a template on mismatch), then run it in front of a zero-shot prompt to the on-prem instruct model on a handful of real cases and have an analyst read the results. That single artifact answers the safety-enforceability question, the "is fine-tuning necessary" question, and gives you your first real data point — before spending a dollar on training infrastructure.

Advisor Responses (full)

The Contrarian downside hunter

The fatal flaw is right in your own setup, and you already named it: you just finished fixing a bug where generated text contradicted an updated verdict. You are now proposing to build a system whose entire job is generating text from case facts, via a fine-tuned model, and asserting "fixed verdict, never re-derived" as if that's a property you can specify into existence. It isn't. LoRA fine-tuning on teacher outputs does not teach a model to treat the verdict field as immutable — it teaches statistical association between case facts and narrative style, including the teacher's phrasing of confidence. A 7B model under distribution shift (a MISP report shape it never saw in training, a classifier score near a decision boundary, an analyzer that errored out) will happily hedge, soften, or flatly restate a different band in prose, because nothing in LoRA training enforces hard constraints — it's gradient descent on token likelihood, not a grammar. Your only real enforcement mechanism is post-hoc: template-lock the verdict/score/confidence as literal injected strings never generated by the model, and regex/parse the output to reject or regenerate anything that emits a competing number or band word. That's not a training-time solution, it's an output-filter solution — which means the fine-tune is buying you narrative fluency, not safety, and the safety has to be built anyway, in the same deterministic style as the system you're augmenting.

Second flaw: "solo lead + AI coding agent + one prior CPU classifier" is not a team that safely ships a hallucination-prone generative layer into a CERT tool. Nobody here has bandwidth to build and maintain that output-validation harness rigorously. Skip the fine-tune; that harness is the actual project.

The First Principles Thinker reframer

First, define the actual job: a translator from structured facts to prose, with a hard non-negotiable — it must never alter, hedge against, or contradict the verdict it's handed. That's not a modeling problem. That's a templating problem wearing a modeling costume.

You already have the deterministic system. The generative add-on's only real job is fluency: turning terse rule outputs and analyzer JSON into readable narrative for non-technical stakeholders. Fluency is exactly what a general-purpose instruct model already does at the 99th percentile out of the box, zero training. The entire distillation pipeline — teacher generation, LoRA, rented GPUs, on-prem deployment, open-source packaging — is being built to solve a problem ("does the model sound natural and cover our report sections") that a good system prompt plus a few hand-written examples already solves.

Ask what the fine-tune is actually buying you. It's not knowledge (analyzer data goes in the prompt either way). It's not verdict-fidelity (a fine-tuned 7B is more likely to drift than a well-constrained prompted model, because fine-tuning teaches it patterns from training data that can generalize past your guardrails — the exact opposite of what "sole authority on verdict" needs). The only thing distillation reliably buys is house style, and you don't need gradient descent for house style — you need a template and a linter.

So the load-bearing question isn't "LoRA vs RAG vs bigger model." It's: have you tried prompting Qwen2.5-7B with structured input and a strict output contract, validated with a deterministic checker, and only reached for training after that demonstrably fails? Nobody described that experiment.

The Expansionist upside hunter

The upside case here is being drastically undersold by framing this as "add-on report generator." First: the fixed-verdict architecture isn't just a safety constraint, it's a moat. Most vendors bolt LLM narration directly onto their scoring, which is why they can't touch it without breaking trust — this team has decoupled verdict-authority from narration-authority. That decoupling is the reusable asset. Once it exists, the same pipeline narrates ANY structured decision the platform makes, not just phishing verdicts: malware triage, incident timelines, threat-intel enrichment summaries, cross-case pattern reports. Scope the fine-tune's input schema generically now and this becomes the narration layer for the whole platform.

Second, undervalued asset: the teacher-generated dataset. Yes it's ToS-encumbered for redistribution, but nothing stops the team from using it internally to spin off adjacent fine-tunes — analyst-facing terse summaries, exec one-pagers, ticket-close notes — all from the same distillation run.

Third: publishing the training pipeline isn't just goodwill — a Thales CERT open-sourcing "how we built a compliant, verdict-locked explanation model" is a recruiting and credibility signal. Bigger swing: don't stop at Qwen2.5-7B for on-prem inference — if this works, build a small internal "report-writing model family" across every deterministic system Thales runs.

The Outsider fresh eyes

Stepping back from all the acronyms: what is being built is "take some data, write a paragraph about it." A person who does this well with a template and a checklist doesn't need to go rent a GPU and grow a whole custom brain to do it. That's the part that reads as confusing to an outsider — the solution is enormously bigger than the problem.

The stated goal is a plain-language narrative for people who are explicitly not technical. That's a formatting/tone problem, not a reasoning problem. Any competent instruct model, prompted with the structured facts and a fixed verdict, already does this. Training a new model doesn't make prose "more plain-language" — it mostly changes style consistency, which a good prompt + template also buys, cheaper and reversible.

On "verdict never re-derived" — nothing about fine-tuning vs. prompting changes whether that's enforceable. The only thing that actually enforces it is a deterministic post-generation validator that scans the output and fails closed if it doesn't match — needed regardless of which LLM route is chosen, and suspiciously similar to the exact bug the team just fixed.

Also: one person is now the data pipeline, the training infra operator, the quality evaluator, AND the deployer, for a security document that goes to outside stakeholders. If this person is out sick for two weeks, who checks the next batch of AI-written verdicts isn't hallucinating? Nobody currently in the described team can.

The Executor Monday morning

Step 1 isn't training — it's a prompted baseline, this afternoon. Zero-shot/few-shot prompt an on-prem instruct model with the fixed verdict + raw analyzer JSON, ask for the narrative. If that output is 80% of the way to "good enough," you have your answer on whether distillation is worth the next six weeks. Nobody should touch LoRA before this exists and has been read by an actual analyst.

The "fixed verdict, never re-derived" constraint is not an ML property, it's a plumbing property — and that's good news. Template-lock the verdict/score/band as a literal injected string, then a cheap regex/JSON-schema validator on every generation checks the output matches the input fact. That's needed whether you fine-tune or just prompt. This is the actual fix for the bug that scared the team — not "train it better," but "never let it assert the verdict unchecked."

Skip the teacher-distillation pipeline until the prompted baseline fails. It's a multi-week detour undertaken by one person with zero prior generative-model training experience, justified only by a hunch.

If you do get to fine-tuning: don't rent GPU compute until you've counted your data. If you can't produce 200+ genuinely distinct historical/synthetic cases with teacher outputs, you have a demo, not a training set — QLoRA on <200 examples on a 7B model is a well-known way to burn a rented A100 overfitting to phrasing.

Open-source framing: solvable but not this week's problem. Publishing code+weights while withholding the dataset is normal (Alpaca did exactly this). Don't let it block anything now.
